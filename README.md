# Instamart Customer Intelligence & Support Copilot

## Overview
Swiggy Instamart delivers groceries, dairy, snacks, personal-care items, and electronics across six Indian metro cities. This repository implements an end-to-end **Customer Intelligence & Support Copilot** solving three operational bottlenecks:
1. **Unreliable raw order exports**: Cleansed and structured into a trusted relational SQLite database with rigorous checkpoint assertions.
2. **Customer churn & segmentation blindness**: Unsupervised RFM clustering identifying actionable personas and supervised lapse prediction scoring churn propensity.
3. **Support desk ticket overload**: Automated triage pipeline featuring PII redaction, token budgeting, fault-tolerant LLM classification, and customer-tier routing.
4. **Autonomous refund resolution & policy assistance**: Grounded TF-IDF policy RAG and ReAct autonomous agent capable of adjudicating refund requests with state checkpoints and crash recovery.

### 2. Cleaning Rules and Transformations

#### Customers Cleaning Rules
1. **City Standardisation**: Stripped leading/trailing whitespace and applied title-casing (`.str.strip().str.title()`). Standardised 24 messy spellings into exactly 6 cities.
   - *Distribution*: Pune (227), Delhi (210), Bengaluru (197), Chennai (191), Hyderabad (191), Mumbai (184). Total: 1,200 customers.
2. **Gender Normalisation**: Mapped 10 non-blank casing variations to `male` (560) and `female` (610). 30 blank/whitespace records were mapped to `unknown` (30).
3. **Age Validation and Imputation**: Replaced 6 values outside [10, 100] with `NaN` (combined with 61 missing = 67 values). Imputed all 67 missing ages using the median age of the customer's standardised city via `groupby('city')['age'].transform('median')`. Result: 0 missing ages, all customer ages between 18 and 60.
4. **Signup Date Conversion**: Parsed raw strings into valid ISO format `YYYY-MM-DD`.

#### Orders Cleaning Rules (Strict Order of Operations)
1. **Timestamp Conversion**: Converted `order_ts` to `datetime64[ns]`.
2. **Exact Duplicate Removal**: Dropped 119 exact duplicate records (`orders.drop_duplicates()`), reducing rows from 13,084 to 12,965.
3. **Latest Record Resolution**: For orders appearing multiple times with pending and final statuses, retained only the record with the latest timestamp per `order_id` (`sort_values('order_ts').drop_duplicates(subset=['order_id'], keep='last')`). Eliminated 656 pending records, leaving exactly 12,309 unique orders.
4. **Order Amount Imputation**: Converted `order_amount` to numeric (coercing unparseable strings to `NaN`). Imputed missing values using the catalogue pricing formula:
   $$\text{order\_amount} = \text{round}(\text{price\_inr} \times \text{quantity} \times (1 - \text{discount\_pct} / 100), 2)$$
   Resolved all 120 missing/unparseable amounts; 0 missing values remain.
5. **Delivery Minutes Treatment**: Coerced 106 negative delivery minutes to `NaN`. For orders with `status == 'completed'`, imputed missing delivery times using the median delivery time of that product's category among completed orders (`groupby('category')['delivery_minutes'].transform('median')`). For orders with `status == 'cancelled'`, delivery minutes were intentionally left `NaN` (1,199 missing) because undelivered orders have no delivery time.
6. **Final Clean Counts**:
   - Total clean rows: 12,309 (11,110 completed, 1,199 cancelled, 0 pending).
   - Missing `order_amount`: 0.
   - Missing `delivery_minutes`: 0 among completed, 1,199 among cancelled.
   - Total completed revenue: **INR 2,998,668.80**.

### 2. K-Means Clustering & Selection of K
The standardized RFM matrix (`StandardScaler`) was clustered for $K \in [2, 8]$ with `KMeans(n_clusters=K, n_init=10, random_state=42)`:

| K | Inertia | Silhouette Score | Business Evaluation |
| :--- | :--- | :--- | :--- |
| 2 | 1820.8 | 0.465 | Under-segmented; blurs frequent shoppers and high spenders |
| 3 | 1268.2 | 0.445 | Transitional state; sub-optimal separation |
| **4** | **743.1** | **0.526** | **Optimal elbow point and highest silhouette score; distinct, actionable personas** |
| 5 | 617.4 | 0.480 | Diminishing returns; splits core segment without distinct actions |
| 6 | 503.2 | 0.482 | Granular fragmentation |
| 7 | 408.5 | 0.416 | Over-segmented; poor boundary definition |
| 8 | 366.5 | 0.412 | Over-fitted; lowest silhouette separation |

*Inertia Explanation*: The inertia of $K=8$ (366.5) is mathematically guaranteed to be lower than that of $K=2$ (1820.8) because increasing the number of cluster centroids strictly reduces the sum of squared distances to the nearest center, converging to zero at $K=N$. Consequently, inertia alone cannot select $K$; model selection requires identifying the inflection point on the elbow curve combined with the peak silhouette score and business interpretability.

### 4. Supervised Lapse Problem Definition & Feature Engineering
- **Cutoff Date**: `2025-09-01 00:00:00`.
- **Cohort**: All customers with at least one completed order before the cutoff (**1,156 customers**).
- **Lapse Target (`lapsed`)**: Ground-truth label is 1 if the customer placed **zero completed orders** in September 2025 (`2025-09-01` to `2025-09-30`), and 0 otherwise.
  - Cohort breakdown: **443 lapsed (38.32%)**, 713 active (61.68%).
- **Pre-Cutoff Feature Set**: Built strictly from orders prior to `2025-09-01`:
  - `recency`, `frequency`, `monetary`, `avg_discount`, `cancellation_rate`, `avg_delivery_minutes`, `favorite_category`, `city`, `age`, `gender`, `tenure_days`.
  - Zero missing values across all features.
- **Data Leakage Safeguards**:
  - No orders dated on or after `2025-09-01` were used in feature extraction.
  - The whole-window RFM segment labels from Task 3 were strictly excluded from features.
  - The dataset was partitioned via `train_test_split(test_size=0.2, stratify=y, random_state=42)`: **924 training rows** (354 lapsed, 570 active) and **232 test rows** (89 lapsed, 143 active).
  - All preprocessing encoders and scalers were fitted **strictly on training rows only** and merely applied to test rows.
- **Train vs Cohort Frequency Mean**:
  - Learned Scaler Frequency Mean (Train): **8.1158**
  - Full Cohort Frequency Mean: **8.0285**
  - *Explanation*: The training set mean differs from the full cohort mean because it represents an 80% stratified sample drawn without leaking the 20% test partition distribution.
- **Baseline Evaluation**: A naive majority-class model predicting "always not lapsed" yields an accuracy of **61.6%** and an F1 score of **0.00** on the lapsed class.

## Part C — Support Ticket Triage with Guardrails

### 1. Input Guardrails & PII Redaction
The raw support dataset (`data/raw/tickets.csv`) contains 164 tickets. Two layers of input guardrails are enforced before any model call:
1. **Input Guardrails**:
   - **Empty / Whitespace Tickets**: 4 tickets (`T0017`, `T0038`, `T0063`, `T0123`) were marked `skipped_empty` and never sent to the model.
   - **Oversized Tickets**: 4 tickets (`T0008`, `T0027`, `T0072`, `T0144`) exceeded `MAX_INPUT_TOKENS = 400` (measuring 734 estimated tokens each) and were marked `flagged_long`.
   - **Eligible Tickets**: Exactly **156 tickets** proceeded to PII redaction and classification.
2. **PII Redaction Pipeline**:
   Sequential regular expressions were applied to sanitize user privacy:
   - **Email**: `r"[\w.+-]+@[\w-]+\.[\w.]+"` $\rightarrow$ `[EMAIL]` (**55 substitutions**)
   - **Phone**: `r"\b[6-9]\d{9}\b"` $\rightarrow$ `[PHONE]` (**91 substitutions**)
   - **Order ID**: `r"ORD-\d{6}"` $\rightarrow$ `[ORDER_ID]` (**132 substitutions**)
   - **Total Substitutions**: Exactly **278 substitutions** across all 164 tickets (0 residual matches remaining).
   - *Prompt Integrity Assertion*: The user message content dispatched to the model is strictly the redacted text and nothing else.

---

### 2. Resilient API Calling & Retry Logic
Calls to `mock_llm.chat` were wrapped in an exponential-backoff retry handler with randomized jitter:
$$\text{wait} = \text{BASE\_DELAY} \times 2^n \times \text{random.uniform}(0.9, 1.15) \quad (\text{BASE\_DELAY} = 0.05\text{s})$$
- Across the 156 eligible tickets, the mock service simulated exactly **19 `TransientLLMError` failures** (every 9th call).
- Every error was intercepted and recovered on retry 0 with a logged sleep duration between **0.0450s and 0.0575s**.
- Result: **0 permanent call failures** across all batches.

---

### 3. Multi-Tier Output Validation
Model responses were parsed and verified across three deterministic tiers:
1. **Tier 1 (`classified_json`)**: Valid JSON with category in `['billing', 'delivery', 'technical', 'fraud']` $\rightarrow$ **135 tickets**.
2. **Tier 2 (`classified_keyword`)**: Non-JSON conversational replies (e.g. *"The customer appears to have a billing-related problem."*) parsed via `re.findall(r"[a-z]+", text.lower())` finding exactly one category keyword $\rightarrow$ **12 tickets**.
3. **Tier 3 (`flagged_invalid_output`)**: Malformed replies or out-of-domain categories (e.g. `{"category": "shipping"}`) $\rightarrow$ **9 tickets** routed directly to human review.
- **Total Classified**: Exactly **147 tickets** (135 JSON + 12 Keyword).

| **Total** | | **15** | (Matches exact reference checkpoint) |

#### TF-IDF Retrieval Mechanics
A scikit-learn `TfidfVectorizer()` was fitted on all 15 chunk texts, with queries ranked using cosine similarity:
- *What TF and IDF Measure*: Term Frequency (TF) measures how frequently a term occurs within a specific chunk, while Inverse Document Frequency (IDF) penalizes common words across the corpus to prioritize distinctive, discriminative keywords.
- *Limitation*: TF-IDF relies purely on exact lexical matching. It cannot recognize semantic equivalence across synonyms or altered syntax (e.g., failing to connect "delayed arrival" with "late delivery" unless those exact words appear in the vocabulary).
- *Top 3 Verification*: For the benchmark query *"refund policy late delivery"*, all top 3 retrieved chunks originated from `refund_policy.txt` (similarity scores: 0.505, 0.448, 0.362).

### 7. Architectural Analysis: ReAct vs. Plan-and-Execute (≤ 250 words)
The ReAct architecture executes a dynamic thought-action-observation loop where each tool result informs the subsequent step. In happy paths like S1 and S2, ReAct requires 5 model calls and ~992 tokens because tool inputs depend strictly on prior outputs (e.g. order delivery time determining whether to invoke `calculate_refund`). Conversely, when terminal conditions or unexpected observations arise—such as an invalid order ID in S6 (`NOT_FOUND`, 2 calls, 110 tokens) or an ineligible cancelled order in S5 (`DENIED`, 3 calls, 394 tokens)—ReAct terminates immediately without wasteful tool calls.

In contrast, a Plan-and-Execute design queries the model once upfront to generate a full static execution sequence (e.g., `get_order` $\rightarrow$ `search_policy` $\rightarrow$ `calculate_refund` $\rightarrow$ `issue_refund`), executing tools deterministically and replanning only upon exceptions. For standard scenarios, Plan-and-Execute achieves superior token efficiency (1 planning call + 1 final synthesis call) and lower latency. However, customer support is fundamentally branch-heavy: an order might be non-existent (S6), cancelled (S5), delivered on time (S4), or exceed escalation thresholds (S3). Plan-and-Execute must either plan speculative multi-branch conditional trees or suffer replanning overhead on every branch divergence.

For this automated refund workflow, ReAct is the superior choice. Its step-by-step grounding prevents premature financial commitments, cleanly halts upon missing records, and integrates seamlessly with step-level state checkpointing for crash resilience.

## Limitations and Next Steps
1. **Post-Hoc Whole-Window Segment Labels**: The `is_premium` tag used to generate the retention list was derived from full 6-month RFM clustering spanning April to September 2025. Because the September window also defines the lapse label, the retention list is illustrative and represents a post-hoc business operationalization rather than an out-of-time evaluation. In a production environment, segment assignments would be recomputed dynamically on rolling historical windows prior to cutoff.
2. **Lexical vs. Dense Vector Retrieval**: TF-IDF relies on exact keyword frequencies. While sufficient for unambiguous policy benchmarks (12/12 fact matches), production deployment would benefit from dense bi-encoder embeddings (e.g. BGE or text-embedding-3) to capture paraphrased customer vernacular and multilingual queries.
3. **Orchestration Scalability**: The current implementation leverages single-threaded state serialization. In enterprise environments, checkpoint state should be persisted to distributed caches (e.g. Redis) with idempotent tool execution keys to support horizontal agent scaling across worker clusters.
